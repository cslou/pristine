Architectural comparison

Pristine vs claude-mem

Two takes on long-term memory for coding agents. One uses Claude to remember Claude. One does it all locally.

Based on claude-mem HEAD beea789 (v12.2.0, pushed 2026-04-18) and pristine branch fix/gemma4-extraction-diagnostic

Why compare these two?

claude-mem is the dominant memory plugin for Claude Code users. Pristine is a local-first TypeScript SDK we're building for the same problem space. Both try to solve: Claude Code forgets everything between sessions.

The headline finding: these two systems make almost opposite architectural choices on every axis. Understanding where claude-mem wins and where it loses sharpens Pristine's design choices.

What is claude-mem?

A persistent-memory plugin for Claude Code. Installed via the plugin marketplace, it hooks every Claude Code tool call and captures a summary, then injects a curated timeline on the next session start.

Target user

Strictly Claude Code users (plus bolted-on adapters for Gemini CLI, OpenCode, Codex, Cursor — same architecture, different hook glue). Not a library. Their own README warns: "npm install -g claude-mem installs the SDK only — it does not register the plugin hooks."

What it does

  • Captures every PostToolUse event from your agent session
  • Asks a second Claude subprocess to summarize what happened, as XML
  • Stores the summary in SQLite + ChromaDB
  • On next SessionStart, auto-injects a "Previously on this project..." timeline as system context
  • Exposes MCP tools so the agent can search memory mid-session

Author & license

Alex Newman (thedotmack). AGPL-3.0. Very active — 232 releases in 8 months, mostly single-maintainer.

The headline finding

claude-mem runs a SECOND Claude to remember the first

Instead of using a cheap model to extract facts, claude-mem spawns a tool-less @anthropic-ai/claude-agent-sdk subprocess running claude-sonnet-4-6 as a "memory observer." It sees every tool call from your real session and emits XML summaries.

// src/services/worker/SDKAgent.ts
const queryResult = query({
  prompt: messageGenerator,
  options: {
    model: 'claude-sonnet-4-6',             // default extraction model
    cwd: OBSERVER_SESSIONS_DIR,             // isolated to hide from `claude --resume`
    disallowedTools: [
      'Bash', 'Read', 'Write', 'Edit', 'Grep', 'Glob',
      'WebFetch', 'WebSearch', 'Task', 'NotebookEdit',
      'AskUserQuestion', 'TodoWrite'
    ],                                       // observer has NO agency
    resume: session.memorySessionId,         // long-running resumable session
    pathToClaudeCodeExecutable: claudePath,
    spawnClaudeCodeProcess: createPidCapturingSpawn(session.sessionDbId),
    env: isolatedEnv
  }
});
Implication: every tool call in your session costs you Sonnet tokens on top of your agent's own tokens. They track this as discovery_tokens. You're paying Anthropic twice — once to code, once to remember.

Hook returns in ~50ms. Observer processing happens async in a subprocess the user never sees. No consolidation step — new observations are appended forever.

Pristine ingestion workflow

┌─────────────────────┐ │ Agent session │ │ (any LLM) │ └──────────┬──────────┘ │ PostToolUse hook fires per turn ↓ ┌─────────────────────┐ atomic tx: write conv + enqueue │ scripts/store.ts │───────────────────┐ │ createLite(), <0.5s │ ↓ └──────────┬──────────┘ ┌──────────────────────────┐ │ │ SQLite │ │ spawn │ conversations table │ │ detached │ pending_ingest_tasks │ ↓ └──────────────────────────┘ ┌─────────────────────┐ │ extract-worker.ts │ self-terminating, 30s idle │ full PristineLocal │ └──────────┬──────────┘ │ │ TWO LLM calls per chunk (local, via Ollama): │ │ 1. EXTRACTOR (gemma4:e4b) │ conversation → facts[] {text, validFrom, │ validUntil, │ temporalConfidence} │ │ 2. CONSOLIDATOR (gemma4:e4b) │ (new fact + top-K similar) → decision │ ADD | UPDATE | NOOP | SUPERSEDE | DELETE │ ↓ ┌─────────────────────┐ │ SQLite + sqlite-vec │ single file, no daemon │ + FTS5 │ nomic-embed-text via Ollama └─────────────────────┘

Hook returns in ~0.1s. Extraction + consolidation happens in a detached worker that exits when idle. Zero external data egress.

Retrieval — claude-mem

Two surfaces, both auto-driven.

1. Auto-inject at SessionStart primary

SessionStart hook ──► GET /api/context/inject?projects=... ↓ Chroma semantic search (90d window) ↓ SQLite hydrate + format as timeline ↓ hookSpecificOutput.additionalContext ↓ Injected as system context, always

2. Agent-invoked MCP tools on demand

// src/servers/mcp-server.ts — MCP tools the agent can call
{
  "search":           "paginated index of past observations",
  "timeline":         "N items before/after anchor observation",
  "get_observations": "full hydrate of specific IDs",
  "build_corpus":     "spawn another Claude session with
                      filtered obs loaded for Q&A",
  "__IMPORTANT":      "fake tool whose description is actually a
                      system instruction enforcing search flow"
}

Search path: Chroma semantic → 90-day filter → categorize by doc_type → SQLite hydrate. FTS5 is built into the schema but rarely routed to.

/tmp/claude-mem/src/services/worker/search/SearchOrchestrator.ts:74-122

Retrieval — Pristine

One surface: a tool the agent decides when to call.

Tool-invoked search on demand

Agent decides it needs memory ──► scripts/search.ts ↓ embed(query) via Ollama ↓ sqlite-vec cosine search ↓ optional temporal filter (current | as_of | full) ↓ top-K memories as JSON to stdout ↓ Agent reads, reasons, answers

Also: scripts/search-conversations.ts for keyword + date search over raw conversations (FTS5, no LLM, no Ollama needed).

What pristine does NOT do

  • No auto-injection on session start — the agent must explicitly call search. Lower hidden cost, higher reliance on agent discipline.
  • No MCP server — integration is via the CLI scripts as skills/tools.
This is a deliberate design axis we can revisit. Auto-injection is powerful but costs tokens on every session; tool-invoked is clean but only works if the agent remembers to search.

Embedder Owned by chroma-mcp (default ONNX, opaque) Nomic Embed v1.5 (768-dim) via Ollama or in-process HF

Operational posture Three-subsystem orchestration Single-file deployment

Pristine's single-file deployment is a genuine win for embeddability, privacy audit, and deploy ergonomics. claude-mem's multi-subprocess setup is richer but harder to reason about when things break.

What a "memory" looks like

claude-mem observation

{
  id: 142,
  memory_session_id: "uuid",
  project: "my-repo",
  type: "bugfix",              // |feature|refactor|change
                               // |discovery|decision
  title: "Fix off-by-one in pagination",
  subtitle: "Loop stopped one short...",
  narrative: "Full prose...",   // 100-400 words
  facts: ["pagination limit is 20",
          "fix is in handlers/list.ts"],
  concepts: ["how-it-works", "gotcha"],
  files_read: ["handlers/list.ts"],
  files_modified: ["handlers/list.ts"],
  prompt_number: 7,
  discovery_tokens: 412,        // cost tracking
  content_hash: "a9f0...",
  created_at_epoch: 1729...
}

Rich. Prose-heavy. Per-tool-call granularity: ~50-200 obs per session.

Pristine fact

{
  id: "uuid",
  user_id: "...",
  text: "User prefers oat milk over almond.",
  embedding: Float32Array(768),
  validFrom: "2023-07-03T00:00:00.000Z",
  validUntil: null,             // or ISO ts for superseded
  temporalConfidence: "inferred",
                                // |explicit|implied|none
  metadata: {source: "voice"},
  sourceConversationId: "uuid", // links to conv store
  contentHash: "...",
  createdAt: "2026-04-17..."
}

Atomic. Statement-level. Per-turn extraction: <10 facts per session.

Different extraction unit = different retrieval ergonomics. claude-mem retrieves richer chunks with titles/narratives, so the answering model has context baked in. Pristine retrieves atomic facts, which compose cleanly but need the answering model to weave them.

Prompt structure — claude-mem

Mode-based system prompt (from plugin/modes/code.json) + per-tool-call XML message generator.

System prompt excerpt

"You are Claude-Mem, a specialized observer tool for creating
searchable memory FOR FUTURE SESSIONS.

CRITICAL: Record what was LEARNED/BUILT/FIXED/DEPLOYED/CONFIGURED,
not what you (the observer) are doing.

You do not have access to tools. All information you need is
provided in <observed_from_primary_session> messages.
Create observations from what you observe — no investigation needed."

Per-tool-call user message

<observed_from_primary_session>
  <what_happened>Edit</what_happened>
  <occurred_at>2026-04-18T10:15:32Z</occurred_at>
  <working_directory>/Users/lou/projects/my-repo</working_directory>
  <parameters>{"file": "src/api.ts", "old": "...", "new": "..."}</parameters>
  <outcome>{"success": true}</outcome>
</observed_from_primary_session>

Return one or more <observation>...</observation> blocks,
or an empty response if this tool use should be skipped.
Never reply with prose outside XML. Non-XML text is discarded.
/tmp/claude-mem/src/sdk/prompts.ts:96-128 and plugin/modes/code.json

Output is parsed by regex — no JSON schema, no response_format. Works because Sonnet 4.6 is disciplined enough to stay in XML.

Prompt structure — Pristine

One system prompt + JSON-Schema-constrained output. Model is a small local Gemma, so the prompt does a lot of work.

You are a memory extraction assistant. Your job is to read
transcripts of conversations and extract factual statements
about the people involved...

Your entire response is a JSON object matching the schema below.
Do not output natural language. Do not treat the schema as a
function call — the response IS the output.

Schema (your response must match this exact shape, with no
markdown fences or prose wrapper):
{
  "type": "object",
  "properties": {
    "facts": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "text": {"type": "string"},
          "validFrom": {"type": "string"},
          "validUntil": {"type": "string"},
          "temporalConfidence": {
            "enum": ["explicit","inferred","implied","none"]
          }
        },
        "required": ["text"]
      }
    }
  }
}

[TASK_DESCRIPTION...]
[CATEGORY_GUIDANCE — 7 personal memory categories...]
[EMPTY_CLAUSE — when {"facts":[]} is legitimate...]
[TWO FEW-SHOT EXAMPLES — rich + empty...]
[TEMPORAL RULES — REFERENCE_TIME, signal types, confidence levels]

Sent with Ollama's format: <schema> parameter for grammar-constrained decoding. Also defended by stripJsonWrapper() for when gemma4 emits markdown fences anyway.

The biggest architectural divergence: consolidation

claude-mem — append-only + recency

  • Every observation is inserted forever
  • Only dedup: content-hash within 30s window (same title+narrative → skip)
  • Retrieval filters to last 90 days
  • No UPDATE, no SUPERSEDE, no DELETE
  • Old facts still live in DB but drop out of search
const DEDUP_WINDOW_MS = 30_000;
function computeObservationContentHash(
  memorySessionId, title, narrative) {
  return createHash('sha256')
    .update([memorySessionId, title, narrative]
            .join('\x00'))
    .digest('hex').slice(0, 16);
}
src/services/sqlite/observations/store.ts:14-46

Drift risk: contradictory observations both surface. Agent has to disambiguate.

Pristine — LLM consolidator

  • Second LLM call per extraction
  • Input: new fact + top-K similar existing memories
  • Output: decision per fact
{
  factIndex: 0,
  action: "ADD"     // brand new fact
       | "UPDATE"   // refines existing
       | "NOOP"     // already captured
       | "SUPERSEDE"// replaces + marks
                   //   old validUntil
       | "DELETE",  // user retracted
  targetMemoryId: "uuid-of-old",
  mergedText: "..."
}

Bounded growth. Coherent long-horizon state. "User currently lives in London."

Flaky on small local models. Truncation bugs (our v2 baseline). Consolidator prompt is the weakest link.

This is the fundamental tradeoff: claude-mem bought simplicity and correctness by using a frontier model + append-only. Pristine bet on structured long-horizon coherence — but is running the wrong-sized model to execute it reliably.

What claude-mem does better

  • Extraction quality. Sonnet 4.6 emits cleaner summaries than gemma4:e4b possibly could. Our extractor prompt has to fight Gemma's function-call priors; Sonnet just does the right thing.
  • Auto-injection UX. Zero agent effort — memory "just works" on SessionStart. Our tool-invoked approach requires the agent to remember to search.
  • Rich observation format. Title + narrative + facts + concepts + files_touched = retrieval returns something the answering model can actually reason over, not atomic fragments.
  • Per-tool-call granularity. Captures intent, parameters, and outcome together — high fidelity for "what did we do last week" recall.
  • Multi-tool distribution. Claude Code, Cursor, OpenCode, Gemini CLI, Codex — all ship with it. Huge mindshare advantage.
  • Web viewer + SSE stream. Observability we just don't have.
  • Corpus Q&A. build_corpus / query_corpus spins up another Claude over a filtered observation slice. Our equivalent would require custom tooling.

What Pristine does better

  • Privacy. Nothing leaves the device. claude-mem sends every tool call including file contents to Anthropic. For regulated data, IP-sensitive code, or offline use, this is the entire game.
  • Cost. $0 at runtime. claude-mem's per-tool-call Sonnet billing scales linearly with activity.
  • Embeddability. Pristine is an actual SDK — you can drop it into any Node app. claude-mem is explicitly a Claude Code plugin.
  • Long-horizon coherence by design. The consolidator can SUPERSEDE/DELETE — contradictory memories get resolved at ingest. claude-mem accumulates contradictions forever and relies on a 90-day cutoff + retrieval to hide them.
  • Single-file deployment. One SQLite file, no daemons, no subprocess zoo, no port management. claude-mem juggles Express + Chroma + observer subprocesses + supervisor + zombie reaper.
  • Temporal reasoning. validFrom/validUntil are first-class on every fact. claude-mem has created_at only — no notion of "this fact stopped being true on date X."
  • Measured behavior. We've run LOCOMO, have Hit@10/MRR numbers, and can A/B prompt changes. claude-mem has no memory-recall benchmarks despite 61k stars. All quality claims are anecdotal.
  • Agent-neutral. Works with any LLM via the Ollama/llamacpp/local embedder engines. claude-mem is Sonnet-first.

Recommendations for Pristine

Adopt

  • Auto-inject on session start. Add an optional hook that runs a search-and-prepend at the start of a conversation. Gate it behind a config flag so users who want strict tool-invoked retrieval can opt out.
  • Richer memory records. Our atomic-fact format composes well but gives the answering model little context. Consider storing a narrative field alongside text — the fact is the index, the narrative is the fetch.
  • MCP server. Expose search / timeline / get_memory as MCP tools so any MCP-aware agent (Claude Code, Cursor, Zed) can use Pristine without custom CLI glue.
  • Observability UI. A local-only web viewer showing memories, recent extractions, pipeline errors. Doesn't need SSE — a simple static page served from the worker is enough. Makes the system legible when things break.

Study

  • Narrow extraction. claude-mem extracts per-tool-call, capturing intent+outcome. We extract from dialogue — harder problem on small models. Consider a per-tool-call extraction mode for coding agent use.
  • Non-LLM consolidation. Replace the LLM consolidator with embedding-similarity-threshold ADD/UPDATE rules. Reserve the LLM for genuinely-close matches. Could eliminate 80% of consolidator calls and the associated failure modes.

Don't adopt

  • The observer-Claude pattern. It's brilliant but defeats our local-first goal. Could offer as a "Sonnet extraction" optional backend but should not be default.
  • Append-only storage. Long-horizon coherence is our differentiator. Doubling down, not backing off.
  • Multi-subprocess architecture. Single-file deployment is a genuine advantage we should preserve.

Strategic positioning

claude-mem owns the Claude Code market through plugin distribution. That's not recoverable. Pristine's position is different:

"Memory that stays yours"

Pristine's differentiators stack cleanly into a single value prop:

  • Privacy: Local-first. Your code, your conversations, never egress.
  • Portable: SDK you embed, not a plugin you install.
  • Coherent: Long-horizon facts with temporal reasoning.
  • Measured: Benchmarks we publish, not vibes.

Who should pick Pristine

  • Privacy-sensitive enterprise (regulated, air-gapped, IP-protective)
  • Product builders embedding memory into their own app, not a Claude Code plugin
  • Research / eval teams needing reproducibility
  • Agents running on non-Claude LLMs (Gemini, Llama, Qwen)
  • Cost-sensitive deployments at scale (100s of concurrent sessions)

Who should pick claude-mem

  • Solo Claude Code users who want memory to "just work"
  • Teams comfortable sending code to Anthropic
  • Users who value the ecosystem (web viewer, corpus Q&A, active development)
Complementary, not competitive. They solve the same problem for different constituencies. The interesting product question is whether Pristine ships an MCP adapter that makes it a drop-in alternative for claude-mem users who want local.
