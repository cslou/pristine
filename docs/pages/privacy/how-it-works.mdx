# How privacy works

Pristine privacy helpers reduce the chance that sensitive values enter agent/model context, third-party LLM requests, or session history in plaintext.

## Composed by the harness

A typical privacy workflow:

1. The host receives text that may contain secrets.
2. The harness calls `detect` to find local candidate `sourceSpan`s.
3. The harness calls `classify` with sanitized context, `[CANDIDATE:<id>]` markers, safe `hint` metadata, and caller-owned policy to decide which candidates are secrets. The SDK does not implement a hosted classifier or bundled LLM classifier.
4. The harness maps `secret` decisions to confirmed `{ sourceSpan, type, label }` inputs and calls `redact` before text enters agent/model context. `uncertain` handling belongs to harness policy.
5. The agent or model sees placeholders instead of original secrets.
6. A trusted local tool runner can call `reveal` when it needs the original value to execute locally.
7. The harness calls `scrubOutput` before tool results or generated output are written back into agent/model context or session history.
8. The harness owns policy, approvals, logging, key handling, backups, and any network services it adds around Pristine.

## Local primitives, deterministic policy

The SDK provides local privacy primitives. Your application still decides where those primitives are called and which behaviors must be enforced every time. Deterministic regex-only behavior can be implemented as a local classifier callback; new integrations should not rely on the legacy `secureAndRedact` composition.

Because agents are non-deterministic, important privacy requirements should not depend on the agent remembering to do the right thing. Put required behavior in harness logic, hooks, command guards, approval flows, logging controls, or local checks, then use Pristine at the text-handling points those workflows create.
